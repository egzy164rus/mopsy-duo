# Архитектура и серверная часть

## 1. Как устроен MVP

```
┌────────────────────────┐        HTTP (JSON)         ┌──────────────────────────┐
│  Клиент (SPA, ES-модули)│ ─────────────────────────▶ │  Node.js HTTP-сервер      │
│  public/js/**           │ ◀───────────────────────── │  server/index.js          │
│  • views/*  • pug.js    │   SSE (realtime-поток)     │  • engine.js — правила    │
│  • core.js  • sfx.js    │ ◀───────────────────────── │  • store.js — данные      │
└────────────────────────┘                            │  • auth.js — сессии       │
                                                      │  • realtime.js — хаб      │
                                                      └──────────────────────────┘
                                                                 │
                                                     data/db.json (MVP)  ⇄  PostgreSQL (prod)
```

Ключевой принцип: **сервер — единственный источник истины**. Клиент не меняет
показатели сам, а присылает намерение («покормить»); сервер проверяет кулдаун,
энергию, состояние сна, применяет эффекты и рассылает всем владельцам новый снапшот.

### Слои

| Файл | Ответственность |
| --- | --- |
| `server/index.js` | HTTP-роутинг, авторизация запросов, rate-limit, статика, запуск |
| `server/engine.js` | Игровые правила: деградация показателей, действия, уровни, задания, достижения, уведомления, снапшот |
| `server/content.js` | Баланс и контент: эффекты действий, скорости убывания, каталог одежды/комнат, пул заданий, достижения |
| `server/store.js` | Хранилище: загрузка/атомарная запись JSON, генерация id, «таблицы» |
| `server/auth.js` | scrypt-хэши, сессии (60 дней), проверка подписи Telegram `initData` |
| `server/realtime.js` | SSE-хаб: подписки по питомцу, персональные рассылки, presence |
| `server/seed.js` | Демо-данные (Аня, Илья и мопс Бублик) |

## 2. Почему SSE, а не WebSocket

В MVP поток данных однонаправленный (сервер → клиент), а действия идут обычными
POST-запросами. Это даёт:

* бесплатную идемпотентность и понятные ошибки (409/429) вместо «молчаливых» сокетов;
* работу через любые прокси и Telegram WebView без настройки upgrade;
* автоматическое переподключение браузера (`EventSource` + `retry: 3000`).

Замена на WebSocket/Supabase Realtime делается в одном месте — `server/realtime.js`
(интерфейс `subscribe / broadcast / onlineIds`) и в `connectStream()` на клиенте.

## 3. Синхронизация двух игроков

1. Каждый клиент открывает `GET /api/pets/:id/stream?token=…` — подписка на питомца.
2. Любое действие → `broadcast(petId, 'state', snapshotFor(pet, viewerId))`.
   Снапшот **персонализирован**: флаги «это моё действие», список непрочитанных,
   признак онлайна партнёра.
3. Партнёр дополнительно получает `pulse` — «Аня кормит Бублика» (тост + звук + вибрация).
4. `presence` — список игроков онлайн; `pushState` вызывается при подключении/отключении.

**Конфликты одновременных действий.** Обработка запросов в Node однопоточна,
поэтому два одновременных «покормить» обрабатываются последовательно: первое
применяется, второе получает `429` с `retryIn` и человеческим текстом
(«Подождите 41 с — «Покормить» уже было совсем недавно»). В PostgreSQL-версии
ту же роль выполняет `select … for update` в транзакции вокруг строки `pets`.

## 4. Защита от накрутки и потери данных

| Риск | Решение |
| --- | --- |
| Двойной тап / повтор POST | `idempotencyKey` на клиенте, таблица `recent_keys` на 120 с (в Postgres — `unique (pet_id, idempotency_key)`) |
| Бесконечные награды | серверные кулдауны на каждое действие + `rateLimit` 60 запросов/мин на игрока |
| Подделка счёта мини-игры | score жёстко ограничивается 0…100, награда считается на сервере, кулдаун 45 с на игру |
| Отрицательные показатели | `clamp(0…100)` на сервере, в Postgres — `check`-ограничения |
| Перезагрузка страницы | состояние живёт на сервере, токен — в `localStorage`; клиент восстанавливает снапшот при старте |
| Сбой/перезапуск сервера | атомарная запись `tmp → rename`, `flush` на SIGINT/SIGTERM |
| Подделка Telegram-профиля | HMAC-проверка `initData` по `TELEGRAM_BOT_TOKEN` (если переменная задана) |

## 5. API

Все ответы — JSON. Авторизация: `Authorization: Bearer <token>`.

| Метод | Путь | Описание |
| --- | --- | --- |
| POST | `/api/auth/register` | `{username, password, displayName}` → `{token, user}` |
| POST | `/api/auth/login` | `{username, password}` → `{token, user}` |
| POST | `/api/auth/telegram` | `{initData}` → `{token, user, trusted}` |
| POST | `/api/auth/demo` | `{who: "anya" \| "ilya"}` — демо-вход |
| POST | `/api/auth/logout` | закрыть сессию |
| GET | `/api/bootstrap` | `{user, catalog, pets, snapshot, dailyBonus, pendingInvite}` |
| POST | `/api/pets` | `{name, color}` — создать мопса |
| POST | `/api/pets/join` | `{code}` — присоединиться по коду |
| GET | `/api/health` |health-чек: `{ok, uptime, realtime}` |
| GET | `/api/pets/:id/stream` | SSE: `state`, `pulse`, `presence` |
| POST | `/api/pets/:id/action` | `{type, idempotencyKey}` |
| POST | `/api/pets/:id/game` | `{game, score, idempotencyKey}` |
| POST | `/api/pets/:id/buy` | `{itemId}` |
| POST | `/api/pets/:id/equip` | `{itemId}` (повторный вызов — снять) |
| POST | `/api/pets/:id/room` | `{roomId}` |
| POST | `/api/pets/:id/task` | `{taskId}` — забрать награду |
| POST | `/api/pets/:id/read` | отметить уведомления прочитанными |

Коды ошибок: `400` неверные данные, `401` нет сессии, `402` не хватает монет,
`403` нет доступа, `404` не найдено, `409` конфликт состояния (`SLEEPING`, `TIRED`),
`429` кулдаун / слишком часто (`retryIn` в мс).

## 6. Баланс

| Действие | Кулдаун | Эффект | Опыт / монеты |
| --- | --- | --- | --- |
| Покормить | 60 с | +26 сытость, +4 настроение | 7 / 3 |
| Дать воды | 45 с | +32 питьё, +2 здоровье | 5 / 2 |
| Поиграть | 90 с | +18 настроение, −12 энергия | 12 / 6 |
| Погулять | 5 мин | +14 настроение, +4 здоровье | 18 / 10 |
| Погладить | 20 с | +9 настроение, +8 любовь | 4 / 1 |
| Искупать | 7 мин | +48 чистота | 10 / 5 |
| Уложить спать | 10 мин | сон 12 мин, энергия +13/ч | 4 / 1 |
| Полечить | 8 мин | +34 здоровье | 9 / 4 |
| Похвалить | 30 с | +12 настроение | 5 / 2 |

Убывание за час: сытость −4.4, питьё −5.2, энергия −3, настроение −3.4,
чистота −2.2, любовь −0.9; здоровье −1.4 при критичных показателях, иначе +0.5.
Оффлайн-время учитывается не более 36 часов — вернувшийся игрок не находит
«мёртвого» мопса. Все числа правятся в `server/content.js`.

Уровни: `90 + (уровень − 1) × 70` опыта, за новый уровень +20 монет.

## 7. Переезд на PostgreSQL / Supabase

1. Выполнить `sql/schema.sql` и `sql/seed.sql`.
2. Заменить `server/store.js` на pg-репозиторий (интерфейс `table.*` совпадает
   с именами таблиц) и обернуть `performAction` в транзакцию:

```sql
begin;
select * from pets where id = $1 for update;          -- блокировка питомца
select * from apply_pet_decay($1);                    -- деградация по времени
-- проверка кулдауна: select count(*) from actions where pet_id=$1 and type=$2 and created_at > now() - interval '60 seconds';
insert into actions (pet_id, user_id, type, text, idempotency_key) values (...);
select * from add_pet_xp($1, 7);
update pets set coins = coins + 3 where id = $1;
commit;
```

3. Realtime-вариант A (Supabase): включить Realtime на таблицах `pets`, `pet_stats`,
   `actions`, `notifications`, подписаться на `pet_id` и убрать SSE.
   Вариант B: оставить SSE, читая изменения из Postgres через `LISTEN/NOTIFY`.
4. Авторизацию можно перевести на Supabase Auth (magic link + `auth.uid()` в RLS),
   сохранив проверку Telegram `initData` для Mini App.

## 8. Планы развития

* Push-уведомления Telegram-ботом по `notifications` (cron + `sendMessage`).
* Совместные сезоны и рейтинги (`v_care_leaderboard`).
* Косметика за реальную валюту через Telegram Stars (`successful_payment` → запись в `inventory`).
* Гонки на сервере для «перетягивания каната» вдвоём (сейчас соперник — личный рекорд).
